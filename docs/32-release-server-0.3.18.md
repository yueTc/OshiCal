# OshiCal 服务端 0.3.18

## 这次修的问题

0.3.16 把预约卡片交给日程模型之后，出现一类新的漏识别：

思诺 2026-11-07 发的动态

> 奥古斯塔是一个很有魅力的人～……感觉今晚吃饭都更香了～
> 下周一18:00继续2.6下哦！

带预约卡片「【2D鸣潮】2.6下！ / 今天 18:00 直播」。这条动态的模型分析结果时间是对的
（`2026-11-09T18:00:00+08:00`），但 `participants` 只写了「心宜」，没有发布者「思诺snow」，
于是 `match_event_target_for_post` 拿「心宜」去和订阅列表比对，找不到任何订阅中的主播，
整条事件被静默丢弃，日历上就没有这一场。

根因有两层：

1. **送进模型的文本里没有作者信息**。`reserve_context(post)` 只拼了正文和预约卡片标题、
   描述，模型不知道这条动态是谁发的，只能按正文里出现的人名判断参与者。正文只提到搭档
   「心宜」，模型就只写了「心宜」。
2. **归属匹配没有兜底**。`match_event_target_for_post` 在名字匹配不上时直接返回 `None`，
   事件被丢掉，日志里也没有痕迹。

同一类问题会影响所有「作者自己发的、正文只写搭档名字」的动态，所以按根因修，不是补丁。

## 改动

### 1. 模型输入带上发布者

`crates/core/src/service.rs` 里拼模型输入时在正文前加一行：

```text
发布者：思诺snow
奥古斯塔是一个很有魅力的人～……
下周一18:00继续2.6下哦！
直播预约：【2D鸣潮】2.6下！
今天 18:00 直播
```

这一行会进入 `text_digest`，缓存键随之变化，历史分析结果自然失效、重新分析。

### 2. prompt 说明发布者与参与者的关系

`crates/core/src/llm.rs` 的 system prompt 增加一段：

> 内容首行「发布者：昵称」标明这条动态由谁发布，它不是直播主题。发布者本人通常就是这场
> 直播的主播：只要发布者是本场直播的参与者之一，`participants` 必须包含发布者的完整昵称，
> 即使正文没有再提到自己；只有正文和卡片都明确说明这场直播与发布者无关（例如纯转发别人
> 的独立直播）时才不要带上发布者。

`prompt_version` 升到 `*-text-v11`，旧版本分析结果不会被复用。

### 3. 归属匹配加作者兜底

`match_event_target_for_post` 在原有精确匹配失败后补一层：

- 只有**单条日程**（`participant_names().len() <= 1`）且 `confidence >= 0.6` 才考虑；
- 动态的发布者本身必须是订阅中的主播；
- 满足条件时把事件归给发布者，并写一条 `debug` 日志
  `event target falls back to the post author`；
- 多人事件仍然要求显式匹配到人，行为不变。

也就是说：宁可把「作者本人发的、但模型写错参与者名字」的场次归给作者，也不要整场丢掉。

## 测试

新增：

- `event_target_falls_back_to_the_post_author`：单条日程、`performer = "心宜"`、发布者是
  「思诺snow」时，事件归属到思诺。
- `reserved_card_event_is_credited_to_the_post_author`：带预约卡片的完整流程，模型给出同槽
  事件后落库一条 `source_kind = text` 的日程，`streamer_id` 是发布者。

既有测试全部保持通过；`cargo fmt --all -- --check`、`cargo clippy -D warnings`、
`cargo test --workspace --locked` 由 CI 执行。

## 升级

```bash
docker compose pull
docker compose up -d
```

升级后对相应主播触发一次刷新即可重新分析动态；分析缓存按新的 `text_digest` 与
`prompt_version` 重新计算，不需要手工清库。

## 已知取舍

作者兜底的代价是：如果发布者真的只是转发别人的独立直播、而模型又把参与者写成了转发对象
之外的名字，这一场会被挂到发布者名下。这种情况在日志里能通过上面的 `debug` 记录定位，
后续可以按需要加白名单或更细的规则。
