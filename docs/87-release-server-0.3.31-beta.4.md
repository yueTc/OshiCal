# 推历 OshiCal 服务端 0.3.31-beta.4 测试版

本版相对 `0.3.31-beta.3` 修复高清图片处理后服务端 RSS 长期维持高位的问题。共享核心的图片准备限流同样会作用于桌面端本地分析；本版只发布服务端，桌面端当前测试版基线保持 `0.3.23-beta.5`。

## 性能与稳定性修复

- 图片解码、缩放和 JPEG 编码增加独立并发限制，无论模型并发数多高，最多同时准备两张图，避免多张 4K/8K 原图叠加放大内存峰值。
- 下载得到的图片字节直接移动进阻塞处理任务，移除处理前的整份内存副本。
- JPEG 降质量重试复用同一尺寸的 RGB 和编码缓冲区，减少重复的大块临时分配。
- 官方容器默认设置 `MALLOC_ARENA_MAX=2`，降低 Debian/glibc 在图片临时分配释放后长期保留 RSS 的概率；使用 `compose.yaml` 时仍可通过同名环境变量覆盖。
- 服务端 API、调度结果、模型请求格式和数据库结构不变；高并发处理大量超大图片时，图片准备吞吐可能因并发从 4 张降到 2 张而略有下降，但单次任务仍完整执行。

## 数据、配置与升级前操作

- 无数据库迁移、API 字段、同步 schema 或默认业务行为变化。
- 升级前停止服务，备份数据库及必要 WAL/SHM、凭据主密钥、环境变量和更新代理配置，并保留旧镜像或二进制。
- 使用官方镜像或仓库内 `compose.yaml` 时无需额外配置；自行部署镜像但未使用最新 `compose.yaml` 时，建议保留镜像内置的 `MALLOC_ARENA_MAX=2`，确需调整时再显式覆盖。
- 本版不执行数据库 `VACUUM`。数据库中的 freelist 空闲页属于文件体积与碎片问题，与本次 RSS 内存修复分开处理，执行前应单独备份数据库并安排维护窗口。

## 适用产物与渠道

- 版本与标签：`0.3.31-beta.4` / `server-v0.3.31-beta.4`。
- 适用 GitHub Actions 生成的 Linux x86_64、Windows x86_64 二进制及 `ghcr.io/yuetc/oshical-server:0.3.31-beta.4` 镜像，实际产物以完成验证的 Release 为准。
- Release 必须标记 prerelease，只维护 `server-beta`；不得移动 `server-latest`、Docker `latest` 或正式版清单。
