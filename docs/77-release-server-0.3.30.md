# 推历 OshiCal 服务端 0.3.30（正式版）

本版相对上一正式版 `0.3.29`，汇总本轮日程日期修正、主播并行刷新、任务共享与识别失败退避、同步历史维护、人数曲线和直播补录卡片改进。建议搭配桌面客户端 `0.3.22` 使用。

## 日程采集与刷新体验

- 无明确日期的周表以动态发布时所在的北京时间自然周（周一至周日）为基准，明确日期与范围优先；“今天/明天/本周/下周”等也基于发布时间，不再随重新分析日期漂移。
- 图片、文字和预约中的有效历史日程保留原日期，已经开始或结束也可以保存；不把旧周表平移到当前周，不为缺失时间或非法日期造日程，不因此虚构开播通知。
- 独立主播刷新按“并行个数”设置同时处理最多 1–8 位，默认仍为 1；同一主播内部保留从旧到新串行。共享官号按 MID 去重，多人联动入库保留一致性保护。
- 图文仅选择前两张图片，超过部分不参与本轮下载、识别及分析缓存身份；相同图片继续复用结果，减少广告尾图导致的重复识别。
- 相同准备范围的全量/单主播刷新会加入进行中的任务、共享进度和结果，而不是重复排队执行。配置、目标或凭据变化不误复用旧任务；部分失败与异常会传播给跟随者，不再被末尾成功提示掩盖。
- Web 全量和单主播手动刷新使用异步作业跟随进度。关闭页面不会取消其他调用者跟随的后台工作，仍可能产生该轮已授权的模型调用和计费。
- 模型识别实际失败后按连续失败次数退避 1、5、15、30 分钟，重启后仍有效；到期后在下一次刷新重试，不新增不断睡眠的后台请求。内容、选中图片或识别配置变化后可立即重新尝试；失败不冒充成功、不删除已有日程。

## 直播卡片、统计与 Web 界面

- 无预告的真实开播自动补建“开播补录”日程卡；前后 2 小时内的有效预告可复用，并与本场直播明确绑定。补卡只遵循日程采集开关，不依赖通知或统计开关。
- 同一直播间下播后 30 分钟内恢复（含边界）按续播处理，保留首次开播时间、卡片和累计统计。跨午夜、重复检查和平台重置开播时间不重复建卡；请求失败不解释为下播。
- 已取消、已删除、被其他场次占用或其他房间的卡片不会误用或被恢复。新增日程和关联通过增量同步发送，Web 无需手动刷新日历。
- 新增人数时间序列及 Web 曲线视图：约每 30 秒保存该窗口内最新的公开高能用户数及原始观测时间，并保留全场峰值；真实下降与 0 保留，断线、未采集和缺失区间不补零。**公开高能用户数不等于全体观众真实同接。**
- 直播数据、人数曲线、扫码登录和模型选择弹层收敛重复的关闭操作，曲线内容独立滚动；保存、迁移等主操作保留。

## 同步历史、数据与 API 兼容性

- 同步历史在启动约 60 秒后首轮维护，之后每小时检查，按 7 天、最新 10,000 条、20 MiB JSON 内容的先到限制清理连续旧前缀。分批最多 256 条并释放写锁；保留上限不包含索引、WAL 和数据库页开销，检查间隔内允许暂时超限。
- 相同日程、来源或不变直播汇总不再反复生成重复快照；实际变化、删除、刷新时间仍正常同步。旧日志过期的离线设备按现有 `resetRequired` 协议重建快照，未发送的本地修改保留。
- 只清理同步历史，不删除订阅、日程、场次或人数采样；不自动执行 VACUUM，也不保证文件立即缩小。需要收回磁盘空间时，应另行安排有备份的维护窗口。
- 启动时自动增量新增 `live_online_samples`、`live_broadcasts`、相关索引及卡片绑定字段，历史观测和绑定不凭空回填。共享 `crates/core` 的日期、采集、无变化保护、轻量直播状态及统计改进也作用于桌面独立模式。
- 新增鉴权接口 `GET /api/live-sessions/{id}/online-samples?afterId=0&limit=500`，返回分页采样与观测时间，`limit` 为 1–1000。完整曲线按需查询，不反复附加到同步快照中。
- `LiveStatus`/`LiveSession` 增加可空 `scheduleId` 及适用的绑定归属信息；旧字段与同步 v2 保持兼容。新客户端能区分服务端明确无绑定与旧服务端未知绑定，不再误高亮其他预告。
- 导入导出快照增加可选轻量直播状态并校验关联、重映射 ID；不扩大原有历史统计和采样的 JSON 迁移范围。完整备份请使用数据库，而不是将 JSON 快照当作全量统计备份。
- 没有新增必填环境变量，现有 Token、模型、代理和宿主机更新代理配置保留。从上一正式版首次刷新可能因分析缓存规则更新而重新调用模型，增加耗时和供应商计费；不需要手动清空所有成功缓存。

## 正式产物与更新渠道

- 正式标签：`server-v0.3.30`。固定镜像：`ghcr.io/yuetc/oshical-server:0.3.30`；正式浮动镜像：`ghcr.io/yuetc/oshical-server:latest`。实际更新以签名清单中的不可变镜像摘要为准。
- 新安装配置模板中的 `OSHICAL_IMAGE` 固定为本版 `0.3.30`，不再指向旧示例版本；不会自动改写用户已有的 `.env`。
- Release 同时提供 Linux x86_64 包 `oshical-server-0.3.30-linux-x86_64.tar.gz`、Windows x86_64 包 `oshical-server-0.3.30-windows-x86_64.zip` 及各自 SHA-256 校验文件；编译包包含 Web 界面资源。
- 本版更新正式 `server-latest` 清单与 Docker `latest`，保留 `server-beta` 测试清单和镜像 `beta`。两端设置均保留 stable/beta；测试渠道同时读取正式与测试清单并选择较高 SemVer，定时更新不会自动降级。
- 由 GitHub Actions 构建、回归、签名和发布。服务端清单使用现有 HMAC 签名；仓库使用 `OSHICAL_SERVER_UPDATE_HMAC_KEY` Secret 签名；宿主机更新代理通过 `OSHICAL_UPDATE_HMAC_KEY_FILE` 指向内容匹配的密钥文件，并保持镜像仓库、版本及摘要检查，不要绕过验签。

## 升级、已知限制与回滚

1. 升级前备份完整 SQLite 数据、环境变量、配置、反向代理与更新代理配置，并保留旧镜像/二进制。使用一致性备份，或停服后连同必要 WAL 备份完整目录，不要只复制正在写入的数据库主文件。
2. 使用设置中的正式渠道和已配置的宿主机更新代理，或部署固定版本镜像；使用编译包时同步替换程序与 `dist`，确认 `OSHICAL_WEB_DIR`、`OSHICAL_DB_PATH` 和既有 Token 配置。
3. 公开网络绑定继续要求安全的 API Token；签名密钥和 Token 不应写入发布页或日志。升级完成后核对健康状态、订阅/日程数量、刷新进度和一场真实直播的卡片关联。
4. 历史未采集的统计不回填；30 分钟内主动下播再开也可能合为续播，提前或迟到超过 2 小时可能保留预告并另补本场卡片。旧错周记录不会保证全部自动修正，应在备份后按来源核对，手动锁定和删除抑制仍有效。
5. 需要回滚时可手动固定 `ghcr.io/yuetc/oshical-server:0.3.29` 或旧编译包。先备份升级后的完整数据；必要时恢复升级前数据库。恢复旧备份会丢失之后的新记录，旧版本不提供本版新增的曲线、补卡和刷新保证，不能用回滚自动清理业务数据。
6. 本次任务发布镜像、编译产物和更新清单，不等同于已经替用户的自托管主机完成部署或生产验收。
