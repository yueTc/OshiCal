1. **当前主要耗时在模型响应，不在数据库写入。** 首轮 279 次模型尝试平均 7.3 秒，P95 达 27.2 秒，且 16 来源中的共享官号串行约束和任务长短不同影响整轮尾部。
2. **缓存轮仍受一条重复失败动态拖累。** 泽音动态 `1100197778887278594`，发布时间为 2025-08-12，原图 8 张，选中前 2 张；两轮均报模型端点发送请求失败。首轮模型失败约 33.275 秒，第二轮约 33.340 秒。没有证据确定是网关、模型上游还是网络具体哪一层，不擅自改超时或跳过内容。
3. 新版限制已在实际输入日志中验证：两轮各有 15 条多于两图的动态，所有实际选图数均不超过 2，原始图片列表未裁剪。
4. 两轮未见 `database is locked`，容器重启 0、OOM=false，最终 health 正常；不据此保证未来任何负载下永不锁等待。
5. 同步清理启动时清了 739 条日志、分 3 批，边界查询 6.671 秒、总计 6.747 秒；边界阶段不持写锁，本次未造成业务锁超时。只读边界查询在此机器上仍有优化空间，但不在本次采样中继续修改。
6. 另有一个单主播请求在排队 60 秒后中断，记录 `outcome=incomplete`。该请求不是两轮完整全量样本，不把它计作完成耗时，也没有通过重启掩盖。
7. 两轮缓存状态不同，不能把 20 分钟与 42 秒之比当成版本优化倍率；本次未取得可比的 beta.2 分阶段基线，也未做并行2与并行3的控制变量测试。

## 后续只读排查：已自动恢复（同日09:01）

上面的两轮样本和当时失败事实不变。用户要求继续排查后，读取后续自动刷新与Nginx日志，得到如下补充：

- 请求链路为 OshiCal → HTTPS Nginx 443 → 本机 WorkBuddy Manager 7864 → 模型网关。
- 08:32:25、08:52:50，Nginx对 `/v1/chat/completions` 记录 **408、响应0字节**，对应此前客户端在08:31:55、08:52:17报发送请求失败；这不是模型返回的业务错误，也没有发现本次请求触发413或64MiB大小拦截的证据。
- 入口设有64MiB请求大小上限、上游响应等待300秒；未设置自定义client_body_timeout，不能把33秒失败直接解释为已配置的模型90秒超时或Nginx上游300秒响应超时。
- Nginx官方文档说明接收请求体超时会返回408，请求缓存开启时完整读取body后才向上游转发。本次证据支持“客户端至入口的请求上传/传输中断”方向，但没有采集当时的网络包、TCP重传或完整reqwest底层错误链，不能进一步定性为MTU、NAT、TLS或网关具体缺陷。
- **08:57:57**，同一条泽音动态自动重试成功，模型阶段 **20.878秒**，结果`[]`正常写入`post-v4`缓存；请求未更换内容或被人工跳过。该轮第一张图片下载还曾耗时59.323秒，说明当时图片链路也有明显网络波动，但不能据此证明两个链路同一根因。
- **09:01:43**，后续完整全量刷新 **6.617秒**，279条全部命中缓存、模型调用0、失败主播0；数据库查询确认所有主播last_error均已清空。该数字是额外的第三种缓存状态，不替换此前42.296秒那轮。
- 排查没有修改模型/代理/超时/缓存/日程数据，没有额外主动发送计费模型请求，只观察现有自动刷新。

结论：故障已由正常自动刷新恢复；可将问题范围缩到请求入口传输超时方向，但底层网络原因仍未证实。建议先补完整异常链、HTTP发送耗时及请求大小诊断，如需改同机网关访问链路应另行确认，不盲目加长超时或删除内容。
