# OshiCal Server 0.3.30-beta.4 发布说明

本版是 `0.3.30` 测试周期的第四个测试版，以下变化相对 `0.3.30-beta.3`。本次只发布服务端；共享任务与失败退避位于共用 `crates/core`，后续桌面版也会获得相应行为，本次桌面端版本不变。

## 本版变化

### 重复刷新直接加入正在进行的任务

- 后台全量刷新期间再次请求相同范围的全量刷新，不再等完后重跑；手动请求直接共享已有任务的最新进度和最终结果。
- 单主播请求可加入覆盖该主播的全量任务，相同主播请求可合并；单主播任务不会被当成全量完成，不同主播或新配置的请求仍保留。
- 等待刷新锁的任务也能被加入，避免重复排队。目标订阅、关联账号、识别配置或凭据变化后，不复用不匹配的旧任务。
- 加入全量任务时明确提示“共享全量结果”，返回的是实际全量统计，不伪装成单主播统计。任务进度不再覆写 API 作业的请求身份，持续点击也能保持去重。
- 服务端 Web 的全量及单主播手动刷新改用现有异步作业接口并跟随进度，部分失败不会再被末尾“刷新完成”覆盖成成功；避免长请求经过反向代理时无进度等待。
- 作业登记和执行使用同一份准备好的配置与目标快照，避免登记后配置变化导致旧任务被误复用。不同范围确需排队时，锁释放后立即继续，不再额外等待轮询间隔。
- 关闭页面或一个等待请求断开，不取消其他调用者正在跟随的后台工作；失败、部分失败和异常退出会传播给所有跟随者，不误报成功。任务结束后再次点击仍发起新刷新，不永久复用旧结果。
- 保留 beta.3 的主播级有界并行：同一主播内部串行；不同范围的整轮任务仍通过原有刷新锁串行，不放开多轮同时写入。

### 识别失败退避重试

- 同一动态的模型识别实际失败后，依连续失败次数安排最早重试时间：第 1 次等待 1 分钟，第 2 次等待 5 分钟，第 3 次等待 15 分钟，第 4 次及以后等待 30 分钟。
- “到期”表示下一次手动或后台刷新可重试，不会新增不断睡眠的后台模型请求。退避期间跳过不会增加次数，也不会不断延长截止时间。
- 普通手动刷新与自动刷新遵守同一规则。退避时仍显示失败原因和北京时间下次可重试时间，不把跳过报告成成功或“无日程”。
- 正文、选中前两张图片、预约、发布时间、模型、端点、提示词、思考参数或凭据变化后，新输入可以立即尝试，不受旧内容的退避阻挡；忽略的广告尾图变化仍不触发重新识别。
- 失败状态持久化，服务重启后仍有效；真正识别成功后清理。失败不写入成功分析缓存，不删除已经保存的日程或来源，继续尊重手动锁定和删除抑制。

## 配置、数据与兼容性

- 不增加表结构、依赖、公开请求字段或必须配置的环境变量。内部失败状态使用既有 `client_sync_state`，不要求手动迁移。
- 不清空 beta.3 成功缓存，分析缓存版本仍为 `post-v4`。前两图限制、历史日程保留与主播并行数不变。
- 任务共享状态仅在当前进程存在；重启后不会恢复进行中的任务。失败退避状态在数据库中保存，不与成功结果混用。
- 退避针对分析器返回的识别错误，不改变 B 站动态抓取错误策略或原有不支持图片的跳过行为。本版不擅自提高模型请求超时、不绕过网关、不扩大动态抓取范围。
- 关闭界面不再意味着后台工作一定终止，仍可能继续产生本轮已授权的模型调用及计费；重复加入同一任务本身不另发一轮调用。
- 识别失败、被退避的来源仍可能使整轮显示“部分来源失败”；需要等待到期刷新或修改相关内容/配置后再试，不应把错误提示消失当作性能优化手段。

## 产物与渠道

- 版本：`0.3.30-beta.4`；标签：`server-v0.3.30-beta.4`；Release 标记为 prerelease。
- 固定镜像：`ghcr.io/yuetc/oshical-server:0.3.30-beta.4`；测试浮动标签：`ghcr.io/yuetc/oshical-server:beta`。
- 版本 Release 提供 `latest-server.json` / `server-latest.json`，同时维护固定 `server-beta` 测试清单；不移动 Docker `latest`、固定 `server-latest` 正式清单或桌面更新清单。
- 编译包：`oshical-server-0.3.30-beta.4-linux-x86_64.tar.gz`、`oshical-server-0.3.30-beta.4-windows-x86_64.zip`，以及相应 SHA-256 文件。
- 编译、测试、签名与发布通过 GitHub Actions，不在用户工作区或部署主机编译。

## 升级验证与回滚

1. 升级前备份数据库、环境变量、反向代理和更新代理配置。活动 SQLite 使用一致性备份，或停服备份完整数据目录，不能只复制正在写入的数据库主文件。
2. 在设置中选择测试版渠道，由已配置宿主机更新代理校验签名与镜像摘要；也可部署上述固定版本镜像。
3. 验证后台刷新期间再次点击是否显示加入进度、是否仅处理一轮，以及已失败动态是否展示下次重试时间；不要为试退避而在生产中故意破坏模型地址或密钥。
4. 需要回滚时可使用 `ghcr.io/yuetc/oshical-server:0.3.30-beta.3`，数据库结构兼容。旧版会忽略新失败退避状态并恢复原刷新排队；若需撤销业务数据变化，应恢复升级前一致性备份。
