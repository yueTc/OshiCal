# OshiCal Server 0.3.30-beta.2 发布说明

本版是 `0.3.30` 测试周期的第二个测试版，以下为相对 `0.3.30-beta.1` 的变化。本次仅发布服务端，桌面端版本保持不变；改动位于共用的 `crates/core`，后续桌面更新也会获得对应解析与存储行为。

## 本版变化

### 历史日程保留

- 开始时间早于当前时刻的有效日程不再被忽略。图片周表、文字动态和直播预约卡均保留原始日期，已经开始或结束的场次也能写入日历。
- 日期明确的历史取消事件同样参与处理。主播、日期、时间和置信度等既有校验仍保留，不为缺少时间或非法日期的内容凭空生成日程。
- 保留 beta.1 的发布周规则：无日期周表、相对日期以动态发布时间为基准，明确日期优先，绝不把上周的场次平移到这周。
- 更新内部缓存版本，避免继续复用旧版过滤历史日程后留下的空结果或不完整结果。新结果正常缓存，重复刷新继续复用同一来源并去重。
- 开播通知仍由真实开播事件触发，补录历史日程不会凭空触发开播通知。

例如：2026 年 11 月 2 日发布的周表在 11 月 10 日重新识别时，11 月 2–8 日的有效场次仍写在原日期，而不是被过滤掉或移到 11 月 9–15 日。

### 同步日志清理

- 调整后台同步日志清理：先在写事务外查找清理边界，并利用已有日期覆盖索引，避免查找期间阻塞日程刷新、直播状态和统计写入。
- 删除日志改为每批最多 256 条，批间释放写锁；每批删除与同步游标边界在同一事务提交，防止客户端读取到不一致的游标。
- 保留原有“按 30 天、保留最新 10 万条”的策略，不删除日程、订阅或直播统计等业务记录。并发新增的同步记录不会被纳入已经确定的清理边界。
- 增加边界查询耗时、批次慢写入/等待和清理总量日志，便于判断是否仍有其他长事务。不能保证所有硬件或其他并发写入场景下完全不发生 SQLite 锁等待。

## 数据、配置与兼容性

- 不新增数据库表或索引，不需要结构迁移，不改变 API，不新增必填环境变量。
- 默认行为有意改变：**已过去的日程也会保存**，因此历史日程条数可能增加。仅处理正常抓取到的动态，不扩大抓取页数，也不自动追溯整站历史或补生过去的周期规则。
- 首次升级刷新会重新分析现有抓取范围内的动态，可能增加模型调用数量、耗时和供应商计费；不需要手动清空所有分析缓存。
- 已存在的错周记录不会仅因升级而保证全部自动修正；应按来源逐条核对。手动锁定与用户删除抑制仍生效，不批量覆盖人工编辑。
- 超出同步日志保留边界的客户端仍按原协议重新拉取快照；分批清理失败时已提交前缀及其游标仍保持一致，后续清理可继续。

## 产物与渠道

- 版本：`0.3.30-beta.2`；标签：`server-v0.3.30-beta.2`；GitHub Release 标记为 prerelease。
- 固定镜像：`ghcr.io/yuetc/oshical-server:0.3.30-beta.2`；测试浮动标签：`ghcr.io/yuetc/oshical-server:beta`。
- 版本 Release 提供 `latest-server.json` / `server-latest.json`，同时维护固定 `server-beta` 测试版清单。
- 编译包：`oshical-server-0.3.30-beta.2-linux-x86_64.tar.gz`、`oshical-server-0.3.30-beta.2-windows-x86_64.zip`，以及 SHA-256 校验文件。
- 构建、测试、发布与签名通过 GitHub Actions 完成；不移动 Docker `latest`、固定 `server-latest` 正式清单或桌面更新清单。

## 升级、验证与回滚

1. 升级前备份数据库、环境变量、反向代理与宿主机更新代理配置。活动中的 SQLite 数据库应使用一致性备份，或停服后备份完整数据目录；不要只复制正在写入的数据库主文件。
2. 设置页选择测试版渠道并确认宿主机更新代理已配置，或部署上述固定版本镜像。更新仍通过签名清单与镜像摘要校验。
3. 升级后完整刷新一次，在日历中切回历史日期检查周表与预约卡，并观察“同步日志清理完成”及慢批次日志；日期仍依赖原图清晰度与模型识别，无法保证所有内容都正确。
4. 如需回滚，可恢复一致性备份并部署 `ghcr.io/yuetc/oshical-server:0.3.30-beta.1`。不恢复备份只回滚程序时，新写入的历史日程仍在数据库中，旧版又会过滤后续历史解析，且同步日志清理占锁风险重新存在。
