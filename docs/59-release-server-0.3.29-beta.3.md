# OshiCal Server 0.3.29-beta.3 发布说明

本版相对 `0.3.29-beta.2`，补齐服务端的渠道切换体验和受控降级能力：用户主动从测试版切回正式版后，服务端会立即读取最新正式版清单并返回可更新状态，再由客户端弹窗询问是否安装。

## 本版变化

### 切回正式版时立即检查

- 服务端更新设置从测试版切换为正式版后，会立即检查最新正式版，而不是等待下一轮定时检查或用户手动点击。
- 设置接口会返回最新正式版、可用状态和检查结果，客户端据此询问用户是否立即更新服务器。
- 当正式版低于当前测试版时，只有用户主动切换渠道并在客户端二次确认后才会提交安装请求；请求继续使用签名清单和固定镜像摘要。
- 自动检测和定时更新仍只安装更高版本，不会后台降级到较低正式版。
- 更新执行期间继续禁止切换渠道，避免更新请求、镜像摘要和渠道状态交叉。

### 宿主机更新代理

- `scripts/oshical-updater-agent.sh` 使用现有的手动更新 `force` 标记授权显式降级，不新增请求字段，旧版本服务端发送的更新请求仍可解析。
- `scripts/update-server.sh` 仅允许“当前为预发布版、目标为稳定版、且请求为手动立即更新”的降级路径；其他降级继续拒绝。
- 降级仍执行镜像摘要校验、停止服务、数据备份、健康检查、目标版本校验和失败自动回滚。
- 升级服务端后，请同步更新宿主机上的两个更新脚本并重新执行更新代理安装或自检，否则旧代理仍会拒绝较低稳定版。

## 数据、配置与兼容性

- 不改变数据库结构或默认配置，无需执行数据迁移。
- 不新增用户必须配置的环境变量；`OSHICAL_ALLOW_DOWNGRADE` 只由宿主机更新代理在手动降级时内部传递。
- 服务端设置接口返回的可更新状态可能包含“当前测试版 → 较低正式版”的显式回退候选，但自动更新不会消费该候选。
- 正式版清单、测试版清单、HMAC 签名和镜像摘要校验规则保持不变。

## 升级前操作

1. 备份服务端数据库、运行配置和反向代理配置，例如：

   ```bash
   cp data/oshical.db data/oshical.db.bak
   cp .env .env.bak
   ```

2. 将仓库中的 `scripts/oshical-updater-agent.sh` 和 `scripts/update-server.sh` 更新到宿主机部署目录。

3. 重新安装或自检宿主机更新代理：

   ```bash
   sudo bash scripts/install-oshical-updater.sh
   sudo bash scripts/install-oshical-updater.sh --check
   ```

4. 部署本版本后确认 `/api/health` 返回的版本为 `0.3.29-beta.3`，并确认更新代理显示在线。

## 回滚

- 自动更新失败时，宿主机会恢复更新前的数据备份和旧镜像。
- 如需从本测试版手动切回较低正式版，请在客户端主动切换正式版并确认降级；服务端不会自动执行该操作。
- 手工回滚前应先停止服务，避免数据库仍写入时覆盖数据文件。

## 已知限制

- 宿主机更新代理脚本必须先更新，旧脚本虽兼容普通升级请求，但仍会拒绝稳定版降级。
- 降级只允许稳定版目标；不会授权预发布版之间或稳定版向更低稳定版的任意回退。
- 真实镜像拉取、容器重启、健康检查和自动回滚由 GitHub Actions 发布及目标宿主机部署验证。
