# OshiCal Server 0.3.30-beta.3 发布说明

本版是 `0.3.30` 测试周期的第三个测试版，以下为相对 `0.3.30-beta.2` 的变化。本次只发布服务端；调度、识别和计时位于共用的 `crates/core`，后续桌面更新也会包含相应行为，本次桌面端版本不变。

## 本版变化

### 主播之间真正并行

- 修复“并行个数”设置存在但全量动态刷新仍逐个主播等待的问题。现在同时处理最多 1–8 个独立主播任务，默认仍为 1；设置为 3 时，最多同时处理 3 位独立主播。
- 同一主播内部仍按发布时间从旧到新逐条分析。本人账号、关联账号和共享官号若涉及同一主播，保留串行顺序，避免改期、取消与来源清理冲突。
- 共享官号按 MID 合并，不按订阅人数重复抓取；独立主播无需等待其他主播的关联来源。多人联动查重与入库有短应用锁保护，图片下载和模型请求不在锁内。
- 进度包含当前处理的主播，整体百分比汇总后不倒退。单个来源抓取或模型失败仍汇总错误，不丢弃其他正常主播的结果；取消事件仍统一收尾处理。

### 每条动态只识别前两张图片

- 正文、预约卡完整参与识别，图片最多下载、处理并发送原顺序前两张；第三张及以后不下载，即使前两张失败也不补图。
- 原始动态完整图片链接仍保存，不删除原始材料。这是用户指定的位置限制，不是广告检测：真正的日程若在第三张以后，也不会识别。
- 图片预算按实际选中的前两张分配，保留单次模型请求与已有图片资源限制；前两图失败时仍可用剩余图片与正文，不额外补发模型调用。
- 缓存内容摘要与图片来源身份只考虑选中图片，尾部广告图片变化不会触发重新识别，前两张、正文或预约变化仍会重新分析。内部分析缓存版本升至 `post-v4`，不复用旧多图结果。

### 分阶段耗时日志与统计

- 新增排队、整轮、来源抓取、图片下载与处理、模型请求、缓存读写、日程查重入库等阶段计时；成功、失败和未完成分别标记。
- 日志通过刷新 ID、来源和动态 ID 关联，不新增密钥、动态正文或图片字节日志。摘要包含模型调用数、缓存命中数、并行数与图片限制。
- 提供 `scripts/summarize_refresh_timing.py`，支持默认文本和 JSON 日志，输出次数、累计/平均/p95/最大耗时及最慢动态。阶段累计可能互相包含、并行重叠，不能相加作为整轮墙钟耗时。
- 使用及字段口径见仓库 `docs/65-refresh-image-limit-and-timing.md`；旧版日志没有采样字段，无法据此生成新统计。

## 数据、配置与兼容性

- 不改变数据库结构或 API，不新增必须配置的环境变量；无需手动迁移数据库。beta.2 的历史日程保留规则继续生效，日期不向当前周平移。
- 并行个数沿用设置 `llm_parallelism`；默认为 1，不会擅自增加模型并发。共享来源依赖、缓存和上游限流会影响实际并发，不保证按倍数加速。
- 首次升级刷新会重新分析正常抓取范围内的动态，耗时与供应商计费可能暂时增加。真实并行会提高瞬时请求、内存和 CPU 使用率，上游限流时请调低并行数。
- 不扩大抓取页数或追溯整站历史，不自动解除手动锁定或用户删除抑制。识别为空不会批量删除旧日程，已存在的错周或广告误识别结果仍需核对。
- 本版不改整轮刷新排队/合并机制，后台任务未结束时再次手动刷新仍可能等待；开播通知继续由真实开播状态触发。

## 产物与渠道

- 版本：`0.3.30-beta.3`；标签：`server-v0.3.30-beta.3`；GitHub Release 标记为 prerelease。
- 固定镜像：`ghcr.io/yuetc/oshical-server:0.3.30-beta.3`；测试版浮动镜像：`ghcr.io/yuetc/oshical-server:beta`。
- 版本 Release 提供 `latest-server.json` / `server-latest.json`，同时更新固定 `server-beta` 测试清单；不移动 Docker `latest`、固定 `server-latest` 正式清单或桌面更新清单。
- 编译包：`oshical-server-0.3.30-beta.3-linux-x86_64.tar.gz`、`oshical-server-0.3.30-beta.3-windows-x86_64.zip`，以及相应 SHA-256 校验文件。
- 所有构建、测试、发布与签名通过 GitHub Actions 完成。

## 升级、验收与回滚

1. 升级前备份数据库、环境变量、反向代理与更新代理配置。活动 SQLite 使用 backup API 等一致性备份，或停服备份完整数据目录，不只复制正在写入的数据库主文件。
2. 设置页选择测试版渠道并确认宿主机更新代理已配置；也可部署固定版本镜像。更新继续校验签名清单与镜像摘要。
3. 升级后执行一轮完整刷新，检查服务健康、不同主播并行、历史日程、前两图选择和数据库错误；再跑缓存命中刷新，按同一模型和并行数比较两轮真实统计，勿把首次重识别直接当作稳定性能。
4. 如需回滚，可恢复旧配置并部署 `ghcr.io/yuetc/oshical-server:0.3.30-beta.2`。仅回滚程序不会删除新生成的日程；如需撤销刷新数据变化，请恢复升级前一致性备份。旧版恢复逐来源串行、多图识别和旧缓存版本。
