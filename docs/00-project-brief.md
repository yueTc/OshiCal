# 推历 OshiCal · 项目启动信息

## 项目启动

- **项目名称**：推历 OshiCal（工程代号：OshiCal）
- **初始需求**：面向 B 站虚拟主播，支持 ID/昵称搜索与订阅；抓取动态、直播预约、文字日程和图片日程；支持桌面端与服务器端；客户端可在本地抓取或使用服务器结果；主体为可点击跳转直播间的日程表；支持开播监控和 Windows 通知；每个订阅可独立控制日程订阅与开播通知。
- **技术栈**：Rust 2021、Tauri 2、Axum 0.8、SQLite、React 19、TypeScript、Vite、OpenAI-Compatible 日程模型接口。
- **是否存在终极功能**：是
- **终极功能定义**：用户订阅主播后，系统能在 20 秒级探测周期内识别开播，并通过 Windows 通知跳转到直播间；同时把文字、预约卡片及图片来源的直播日程可靠汇总到统一日程表。
- **技术约束**：Windows 10/11 优先；WebView2；单用户服务器；订阅规模约 20 个主播；开播探测默认 20 秒，可在设置中调整；服务端事件在发现变化后 1 秒内通过 WebSocket 推送；日程时区固定为 Asia/Shanghai。
- **默认循环轮次**：3
- **安全最大轮次**：6
- **每轮最大改动点数**：3
- **角色配置**：主控 + 架构师 + 程序员 + 测试员

## 业务目标

让用户不再手动逐个翻看 B 站个人号与官号动态，在一个日程表中掌握直播安排，并在主播开播时立即收到可点击的 Windows 通知。

## 成功标准

1. 输入 B 站昵称或 UID 可搜索并添加订阅。
2. 本地模式与服务端模式都能展示订阅、日程和开播状态。
3. 文字动态、直播预约卡片和图片日程进入统一日程表。
4. 动态文字和图片分别结构化；同一文字版本、同一图片各只调用一次模型，结果按主播归属后复用。
5. 点击已确认日程可打开对应直播间。
6. 开播状态从 false 变为 true 时只通知一次；点击通知可打开直播间。
7. 每个订阅分别保存“订阅日程”和“开播通知”开关。
8. 服务器断开后客户端自动重连，并补齐遗漏事件。

## In scope

- B 站账号搜索、订阅、取消订阅。
- 主账号与多个官号关联。
- 动态抓取、文字日程解析、直播预约卡片解析。
- 动态文字和图片的模型结构化提取、共享分析与主播归属。
- 日程确认、手动新增、删除。
- 本地/服务器数据源切换。
- Windows 原生通知与直播间跳转。
- 单用户服务器、Bearer Token、WebSocket 推送。
- SQLite 本地缓存和服务端持久化。

## Out of scope

- 多用户注册、团队权限、付费订阅。
- 手机原生 App。
- 自动登录 B 站、绕过验证码或风控。
- 全自动处理所有自然语言和所有图片排版。
- 长期重复日程自动生成。
- 直播录制、弹幕抓取、视频下载。
- 云端托管和商业运维平台。

## 已声明假定

- 用户使用 Windows 10/11，并允许系统通知。
- B 站公开接口可能触发风控，因此提供可选 SESSDATA；缺少 Cookie 时允许降级。
- 日程模型由用户自行提供 OpenAI-Compatible 服务与凭证。
- 周表未标日期时按动态发布时所在的北京时间自然周解释，正文或图片的明确日期优先；相对日期以发布时间为基准，已过去但日期时间明确的日程仍写入原日期，不顺延到当前周。
- 低置信度或无法唯一归属的图片日程直接丢弃。

## 补充成功标准（2026-10-26 第二轮澄清）

1. 动态与官号日程默认每 5 分钟刷新一次，允许配置 5–60 分钟，手动刷新始终可用。
2. 日程默认显示所选日期起连续 7 天，每次前进/后退移动 1 天，并提供回到今天。
3. 日历网格与时间线视图均可选择。
4. 关闭窗口后驻留系统托盘；设置页提供默认关闭的开机自启开关。
5. 手动新增、修改、删除日程在本地和服务器模式都始终可用；离线操作进入本地同步队列。
6. 服务器数据单向导入客户端，服务器不被导入流程修改；冲突由用户查看摘要后统一选择处理策略。
7. 官号只用于日程抓取，不参与开播监控，不产生官号开播通知。
8. 第一版不做开播前提醒，只通知实际开播。
