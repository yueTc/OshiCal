# OshiCal Server 0.3.29-beta.2 发布说明

本版相对 `0.3.29-beta.1`，新增同槽重复日程合并修复；上一测试版引入的正式版/测试版更新渠道继续保留。桌面端与服务端共用 `crates/core`，桌面端 `0.3.21-beta.2` 同步包含本修复。

## 本版变化

### 重复日程修复

- 同一主播、同一开始时间、同一直播间的预约卡、图文和文字识别结果会合并为一张日程卡片，不再同时出现多条近似记录。
- 去重范围从多人团播扩展到单人场次；只要时间槽、参与者和直播间信息足以证明是同一场，就会自动合并。
- 预约卡与图文识别给出不同标题时，保留预约卡中的官方标题；后续识别出的结束时间和来源仍会合并保留。
- 下一次完整刷新后，历史遗留的同槽重复日程会自动合并，无需手工逐条删除。

### 更新渠道

- 服务端设置页继续提供 `stable`（正式版）与 `beta`（测试版）更新渠道。
- 测试版渠道同时检查测试版和正式版服务器清单，并按 SemVer 选择更高版本；正式版达到更高版本后，测试版服务端可以升级回正式版。
- 更新执行期间禁止切换渠道，避免清单、镜像摘要和更新请求跨渠道混用。
- 测试版使用独立的 `server-beta/latest-server.json` 签名清单和预发布 Release，不会移动 Docker `latest`、`server-latest` 或桌面端 `latest`。

## 数据、配置与兼容性

- 不改变数据库结构、API、环境变量或默认配置，无需执行数据迁移。
- 不会删除手动锁定的日程；自动合并只处理未手动锁定的自动来源。
- 合并后会保留各自动来源与日程的关联，后续取消、改期和来源追踪仍可继续工作。
- 尚未触发刷新前，已有重复不会立即消失；等待下一轮刷新，或在客户端手动刷新受影响主播即可触发合并。
- 只有时间差在 10 分钟内，并且参与者有足够重合或直播间归属一致的记录才会合并；无法证明为同一场的不同直播间仍会保留。

## 产物与渠道

- 镜像：`ghcr.io/yuetc/oshical-server:0.3.29-beta.2`
- 测试渠道浮动标签：`ghcr.io/yuetc/oshical-server:beta`
- 签名清单：`server-beta/latest-server.json`，同时提供版本 Release 的 `latest-server.json` 与兼容清单 `server-latest.json`
- 编译产物 Release：`server-v0.3.29-beta.2`
- 编译包：`oshical-server-0.3.29-beta.2-linux-x86_64.tar.gz` 与 `oshical-server-0.3.29-beta.2-windows-x86_64.zip`

## 升级前操作

1. 备份服务端数据库与环境配置，例如：

   ```bash
   cp data/oshical.db data/oshical.db.bak
   cp .env .env.bak
   ```

2. 继续使用测试版渠道，或显式选择上面的镜像版本。

3. 升级前确认宿主更新代理所需的 `/etc/oshical/updater-hmac.key` 已按现有部署规范配置。

4. 升级后确认 `/api/health` 返回的版本为 `0.3.29-beta.2`，再刷新受影响主播并检查重复卡片是否合并。

## 回滚

若升级后出现异常，可重新部署 `0.3.29-beta.1` 镜像，或停止服务后恢复升级前的 `oshical.db` 与配置备份。回滚前请先停止服务，避免数据库仍在写入时覆盖文件。

## 已知限制

- 本次修复不会合并“同一时间确实是两个独立直播间”的合法并存场次。
- 本机构建受限，Rust 测试与真实刷新验证需由 GitHub Actions 或指定外部构建机完成。
