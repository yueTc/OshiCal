# OshiCal Server 0.3.30-beta.1 发布说明

本版是 `0.3.30` 测试周期的首个测试版，相对上一发布版本 `0.3.29` 修复旧动态周表被错误排入当前周的问题。仅推进服务端版本；日期解析位于共用的 `crates/core`，后续桌面端更新也会包含该修复，本次不发布或变更桌面端版本。

## 本版变化

- 修复重新分析旧动态时，无具体日期的周表被套用到分析当天所在周的问题。周表现在以动态**发布时所在的北京时间自然周（周一至周日）**为基准。
- 图片或正文中的明确日期、日期范围仍优先；“今天”“明天”“本周”“下周”“上周”等相对日期以动态发布时间为基准，不随刷新日期漂移。
- 明确禁止把已过期的周表平移到当前周或未来周来生成日程；已有的过去日程过滤和明确取消事件处理保持不变。
- 文字与图文分析同步修正，并更新内部分析缓存版本。升级后重新分析动态时不会继续复用旧日期规则生成的缓存；自定义提示词版本同样生效。
- 补充跨周、北京时间与 UTC 跨日、跨年周范围，以及新旧缓存隔离的回归用例。

例如：2026 年 11 月 2 日发布、没有具体日期的周表，在 11 月 10 日刷新时，仍归属 11 月 2–8 日，不再被排入 11 月 9–15 日；正文明确写“下周”或给出其他日期范围的，以原文为准。

## 数据、配置与兼容性

- 不改变数据库结构、API 或默认更新渠道，不需要数据库迁移，不新增必填环境变量。
- 首次刷新会重新分析动态，可能暂时增加模型请求数量、耗时及供应商计费；新的分析结果继续按原有规则缓存。
- 保留“分析失败或返回空结果时不批量删除历史日程”的保护。因此，**升级不会自动清除已经保存的错周日程**。请在备份后逐条核对来源，并通过日程管理删除确认错误的记录；不要批量删除全部周表或人工日程。仅升级、不核对已有记录，界面中仍可能保留此前生成的错周日程。
- 手动锁定、来源抑制、预约卡兜底与同槽去重行为不变。

## 产物与渠道

- 版本与发布标签：`0.3.30-beta.1` / `server-v0.3.30-beta.1`，GitHub Release 标记为 prerelease。
- 固定版本镜像：`ghcr.io/yuetc/oshical-server:0.3.30-beta.1`。
- 测试版浮动镜像：`ghcr.io/yuetc/oshical-server:beta`。
- 更新清单：版本 Release 内的 `latest-server.json` / `server-latest.json`，同时维护固定 `server-beta` 测试版清单 Release。
- 编译包：`oshical-server-0.3.30-beta.1-linux-x86_64.tar.gz`、`oshical-server-0.3.30-beta.1-windows-x86_64.zip`，以及相应 SHA-256 校验文件。
- 构建、发布、签名及产物验证通过 GitHub Actions 执行；不移动 Docker `latest`、固定 `server-latest` 正式版清单或任何桌面端更新清单。

## 升级前操作与已知限制

1. 升级或删除已确认错误的日程前，备份数据库、环境变量、反向代理及更新代理配置。活动中的 SQLite 数据库请使用一致性备份（SQLite backup API），或停服后备份完整数据目录，不要直接复制正在写入的单个数据库文件。
2. 使用设置页更新的用户需切换至“测试版”渠道，并确保宿主机更新代理已正确配置；更新仍使用签名清单和镜像摘要校验。使用容器部署的用户也可指定上述固定版本镜像。
3. 升级后执行一次完整刷新，核对周表的来源动态、发布日期与实际日期，并按前述方式处理已保存的错误记录。
4. 模型识别仍依赖原图清晰度和上游输出，不能保证所有周表都能正确识别；没有足够日期依据的非周表内容仍不猜测日期。
5. 如需回滚，可恢复备份并使用 `ghcr.io/yuetc/oshical-server:0.3.29`。旧版仍有本次修复的错周风险；回滚程序不会自动恢复已手动删除的记录，请保留备份。
