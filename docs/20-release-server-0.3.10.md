# OshiCal Server 0.3.10

本次仅发布服务端，标签为 `server-v0.3.10`。桌面端保持 `0.3.5`；本轮桌面端「进入直播间」菜单的改动已在 `main`，随下一次桌面端发布一起出包。

## 预约动态：正文里的另一场单独入库

带 B 站直播预约卡片的动态，原先只要卡片能生成日程就不再解析正文，于是正文里另写的场次（例如卡片是「明天 06:00 比赛」，正文又写「*今晚20:00来杂谈」）会丢。

本版本改为：

- 卡片那一场仍以预约为准；正文里与预约时间相同（±10 分钟）的条目丢弃，不重复入库。
- 正文若还有另一个时间点，仍然进入文字模型并单独生成日程，不再因为本条动态带预约就整段跳过。
- 是否「还有一场」由逐行时间解析判定：只要有一行能解析出与预约不同的日期时间就放行；预约时间解析不出（只有星期几、只有时间）或卡片是视频预约（`stype=1`）时，卡片不生成日程，正文照常解析。
- 预约动态里的 `cancel` 不采信：取消仍由不带预约的公告触发，避免预约卡片把正常日程删掉。

## 正文识别不再依赖语序

提示词与解析补强：

- 「时间写在事项前面」的常见写法（`6:00来看IG VS geng四强战`、`今晚20:00来杂谈`、`*明晚8点 歌回`）都能识别。
- 忽略行首的 `*`、`·`、`-`、`👉`、`①` 等项目符号。
- 「来看XX比赛」「来杂谈」这类口语按直播日程处理，陪看、转播、解说同样算直播。
- 每个带时间的事项都单独输出，不会因为已经有别的条目就只挑一条。

## 动图不再进视觉模型

GIF、动图原先会走图片下载再被格式校验拒掉，日志里表现为「图片格式只支持 JPEG、PNG 或 WebP」的失败。现在：

- `ContentAnalyzer::analyze_image_url` 改为返回 `AppResult<Option<LlmAnalysis>>`，`Ok(None)` 表示「主动跳过」。
- 用 `Content-Type` 加文件头（`GIF87a` / `GIF89a`）双保险判定，CDN 把 GIF 标成 `image/png` 也能识别。
- 跳过不算失败，不记主播错误，也不占模型调用。

## 同时包含 0.3.9 的生理期修复

0.3.9 的「接口不再同步抓取 + 采集单飞 + 数据源可用 `OSHICAL_FERTILITY_URL` 覆盖」一并在本版本内。

## 兼容性

- 响应结构不变；`/api/fertility` 在缓存过期时先返回 `stale=true` 的缓存并在后台刷新。
- 桌面端 `0.3.5` 无需改动即可兼容（`analyze_image_url` 的 `Option` 只在服务端内部使用）。
- 已有数据库与 `fertility_cache` 直接复用，无需迁移。

## 验证

- 本机只做源码与格式检查（`cargo fmt --all -- --check`），不执行构建、Clippy 或测试。
- Rust 格式、Clippy（`-D warnings`）、前后端测试与服务器镜像由 GitHub Actions 验证并发布。
