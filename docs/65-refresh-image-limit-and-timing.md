# 动态前两图识别与刷新耗时统计（开发分支）

本文件说明 `codex/streamer-parallel` 中尚未发布、部署的改动，不代表当前线上版本已经生效。

## 图片策略

- 每条动态只下载、处理并发送原顺序前两张图片，正文和预约卡继续完整处理，仍然只调用一次模型。
- 0/1/2 张图片正常处理；有更多图片时，第三张及以后不下载，不作为前两张失败时的替补。
- 前两张下载或处理失败时，继续使用剩余可用图片和正文；不因此自动补发其他图片或第二次模型请求。
- 原始动态完整图片列表仍保存在数据库中，不删除用户原始材料。模型输入与缓存摘要只使用前两张，忽略尾图变化；正文、预约卡或前两张变化仍会重新分析。
- 内部缓存后缀改为 `post-v4`，不复用此前包含多图广告内容的模型结果。首次刷新会重新分析抓取范围内的动态，耗时和计费可能暂时增加。
- 这是用户指定的位置限制，不是广告检测；真正的日程若在第三张以后，也不会被识别。已有错识别结果不会因新结果为空而被批量删除，必要时需核对来源。
- 共用 core 同时供服务端和桌面使用，后续发布都将遵循该限制；本次不自动修改桌面版本。

## 日志采样

所有阶段使用单调时钟。日志只包含阶段、微秒耗时、结果及用于关联的刷新/来源/动态标识，不新增密钥、动态正文或图片字节日志。

| phase | 口径 |
|---|---|
| refresh_round | 一次刷新请求的实际墙钟耗时，包含排队与初始化 |
| refresh_queue_wait | 等待上一轮刷新锁的时间 |
| source_pipeline | 动态来源处理、结果汇总与收尾的实际耗时 |
| source_refresh | 单个来源处理耗时 |
| source_fetch | B 站动态抓取 |
| post_store | 保存原始动态 |
| cache_lookup / cache_store | 模型结果缓存读取/写入 |
| model_slot_wait | 模型并发许可等待 |
| image_download | 单张选中图片的下载与读取 |
| image_prepare | 图片缩放/压缩/编码，包含后台处理队列等待 |
| model_request | 模型请求、传输重试、响应读取与解析 |
| post_analysis | 一条动态的图片准备和模型调用合计 |
| schedule_upsert | 日程查重、合并和落库，包含应用级写入保护等待 |

正常返回记录 `outcome=ok`，错误返回记 `error`，被中断或未完成记 `incomplete`。一次请求返回部分来源失败时，摘要的 `failed_streamers` 也需要检查，不能仅把一个阶段的 ok 当作整轮无错误。

全量及单主播刷新都有独立 `refresh_id`，来源日志有 `source_mid`，图片/模型/入库日志可通过 `post_id` 关联。缓存命中不会伪造模型调用耗时；摘要同时记录模型调用数、缓存命中数、并行数和图片限制。

## 汇总真实日志

在包含本脚本的仓库目录，用 UTF-8 日志文件执行：

```bash
python scripts/summarize_refresh_timing.py refresh.log --latest
python scripts/summarize_refresh_timing.py refresh.log --refresh-id <刷新ID> --json
```

也可从部署宿主机的日志管道读取：

```bash
docker logs --since 30m oshical-test 2>&1 | python scripts/summarize_refresh_timing.py --latest
```

脚本支持默认文本日志（包含 ANSI 颜色）及 JSON tracing 日志，输出各阶段次数、累计/平均/p95/最大毫秒数、错误/未完成次数，以及耗时最高的动态。`--latest` 选择最后出现的刷新标识；没有符合记录时返回非零退出码，不生成虚构统计。

**不能把阶段累计时间相加当作整轮实际耗时。** 图片准备包含下载之外的处理，单动态合计又包含模型时间；并行主播时间也互相重叠。只有完成的 `refresh_round` 是整轮墙钟记录；被中断的 round 不会被汇总成已完成耗时。

建议分别保存一次首次分析刷新和一次缓存命中刷新，固定并行数与模型后比较；不要把不同动态或不同缓存状态的两轮结果直接当作优化倍率。

## 验证及上线边界

- 所有编译、测试和产物验证走 GitHub Actions，本地只格式化与静态检查。
- CI 使用可控图片加载器和模型 HTTP fixture 验证没有第三张下载、坏图不补、一次模型请求及完整原图留存；不会拿 fixture 的耗时冒充真实服务器性能。
- 要获得真实服务端分阶段统计，必须先发布并部署包含采样的新版本，再完成至少一轮刷新。旧版日志没有这些阶段数据，不能据旧日志精确推算。
